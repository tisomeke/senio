# Git Workflow — Senio

Единые правила работы с Git и GitHub для команды Senio.

**Основной принцип:** одна задача — одна ветка — один Pull Request (PR). Все изменения проходят через PR и проверяются перед слиянием в `main`.

## 1. Работа с задачей

Перед началом работы:
1. Найди назначенную задачу в GitHub Issues и ознакомься с критериями готовности.
2. Убедись, что никто не работает над теми же изменениями без согласования.
3. Создай отдельную ветку от актуальной `main`.

```bash
git switch main
git pull origin main
git switch -c docs/improve-readme
```

Указывай собственное название ветки в последней команде. Не вноси изменения непосредственно в `main`.

## 2. Именование веток

Формат: `тип/краткое-описание`.

| Префикс | Назначение | Пример |
|---|---|---|
| `feat/` | Новая функциональность | `feat/material-search` |
| `fix/` | Исправление ошибки | `fix/search-results` |
| `docs/` | Документация | `docs/improve-readme` |
| `test/` | Написание или изменение тестов | `test/catalog-tests` |
| `chore/` | Вспомогательные технические задачи | `chore/add-senka-assets` |
| `refactor/` | Изменение структуры кода без изменения поведения | `refactor/search-service` |

Правила:
- Используй английский язык, нижний регистр и дефисы между словами.
- Выбирай название, отражающее суть задачи.
- Не используй пробелы, кириллицу и расплывчатые названия вроде `my-branch` или `new-changes`.
- Для каждой новой задачи создавай новую ветку.

## 3. Правила коммитов

Формат сообщения: `тип: краткое описание`.

| Тип | Пример |
|---|---|
| `feat` | `feat: add material search` |
| `fix` | `fix: correct search results` |
| `docs` | `docs: improve project README` |
| `test` | `test: add catalog tests` |
| `chore` | `chore: add Senka assets` |
| `refactor` | `refactor: simplify search logic` |

Сообщения пишутся на английском языке. После двоеточия — описание с маленькой буквы.

Хороший коммит описывает конкретное изменение. Избегай сообщений `update`, `changes`, `some fixes` и `work`.

Перед коммитом проверь изменения:

```bash
git status
git diff
```

Добавляй только файлы, относящиеся к задаче:

```bash
git add README.md
git commit -m "docs: improve project README"
```

***Не добавляй случайные файлы, личную информацию, секреты, пароли, токены или локальные настройки.***

## 4. Отправка изменений

Отправь ветку на GitHub:

```bash
git push -u origin docs/improve-readme
```

При первом отправлении ветки используется `-u`. При последующих отправлениях достаточно `git push`.

## 5. Pull Request и связь с задачей

Каждый Pull Request (PR) **обязательно должен быть связан с GitHub Issue**, в рамках которой выполнялась работа.

### Создание PR

1. Создай PR из своей ветки в `main`.
2. Укажи понятный заголовок и кратко опиши изменения.
3. В описание добавь ссылку на Issue.

Если PR полностью завершает задачу, используй ключевое слово `Closes`:

```text
Closes #2
```

При слиянии такого PR в `main` GitHub автоматически закроет Issue № 2.

Если задача ещё не завершена и потребуются другие PR, используй обычную ссылку без автоматического закрытия:

```text
Refs #2
```

Вместо `2` укажи номер своей задачи.

## 6. Проверка и слияние

1. Дождись проверки PR ответственным участником команды.
2. Если есть замечания, исправь их в той же ветке и отправь новые коммиты.
3. Не создавай новый PR для исправлений к уже открытому PR.
4. После одобрения ответственный за слияние объединяет PR с `main`.

Не сливай собственный PR без согласования с командой. Не переписывай историю общей ветки и не используй принудительную отправку (`git push --force`) без согласования.

## 7. После завершения

Обнови локальную `main`:

```bash
git switch main
git pull origin main
```

После успешного слияния рабочую ветку можно удалить, если она больше не нужна:

```bash
git branch -d docs/improve-readme
```

Вместо `docs/improve-readme` укажи название своей завершённой ветки.

## Главное

- Не работаем непосредственно в `main`.
- Одна задача — одна ветка — один PR.
- Используем единый формат названий веток и коммитов.
- Проверяем изменения до отправки.
- Обсуждаем и проверяем изменения перед слиянием.
- Если не уверен в команде или возник конфликт, не пытайся исправлять его наугад — обратись к команде.
