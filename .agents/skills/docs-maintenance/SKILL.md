# Skill: docs-maintenance (SENIO)

Переиспользуемый процесс сопровождения документации проекта SENIO:
аудит, актуализация и поддержание согласованности всех документирующих
файлов репозитория.

## Когда активируется

- пользователь просит обновить, проверить или пересмотреть документацию;
- изменения в коде, архитектуре или инфраструктуре требуют актуализации
  документов;
- пользователь просит провести аудит документации;
- пользователь просит проверить соответствие документации текущей
  реализации.

## Процесс

### Шаг 1. Аудит перед изменениями

1. Изучи структуру репозитория и состояние Git (`git status`,
   `git log`, список файлов). Различай изменения текущей ветки,
   смерженные изменения и функциональность, которая существует только
   в открытых PR. Если PR нужно проверить, а `gh` недоступен, сообщи об
   ограничении, а не предполагай.
2. Найди все документирующие файлы: `README*`, `docs/`, `dev-docs/`,
   `AGENTS.md`, инструкции для разработчиков и другие материалы.
   Не ограничивайся заранее заданным списком.
3. Прочитай действующие `AGENTS.md` и следуй им; они имеют приоритет
   над этим Skill в вопросах проектного контекста.
4. Проверь документацию на противоречия, устаревшие сведения и
   дублирование.
5. Сопоставь документацию с действительным состоянием кода,
   конфигурации и инфраструктуры: наличие файлов, команд, сервисов и
   проверенных инструкций запуска.
6. Если документы противоречат друг другу или `AGENTS.md` противоречит
   сам себе, не выбирай вариант молча: сообщи о противоречии и запроси
   решение.

### Шаг 2. Актуализация

Обновляй только те документы, которые действительно существуют и
затронуты изменениями. Не создавай документы ради заполнения
структуры.

- `AGENTS.md` — инструкции и контекст для ИИ-агентов;
- `README.md` — описание проекта и основные способы взаимодействия с
  ним;
- `docs/` — проектная документация;
- `dev-docs/` — документация разработчика, включая пользовательские
  сценарии;
- инструкции по настройке, запуску и архитектуре;
- документацию API, моделей данных, инфраструктуры и CI/CD.

Правила и рабочие процессы команды (например, Git Workflow) не
переписывай здесь: обновляй профильный документ и оставляй ссылки.

### Шаг 3. Проверка качества после редактирования

- проверь согласованность терминологии и технических сведений между
  документами (включая русскую и английскую версии, если обе затронуты);
- проверь соблюдение правил оформления текста из `AGENTS.md`,
  раздел 11: русская типографика в документации, только клавиатурные
  символы в коде и служебных текстах;
- проверь внутренние ссылки и пути к файлам;
- проверь команды и инструкции на соответствие текущей реализации;
- убери устаревшие инструкции и противоречия;
- не создавай дублирующие документы: добавляй подробности в
  существующий профильный документ;
- убедись, что документация не обещает функциональность, которой ещё
  нет;
- не переноси в документацию секреты и содержимое локальных
  `.env`-файлов.

## Принципы

1. **Документация должна отражать реальность.** Не описывай
   предполагаемую архитектуру как существующую.
2. **Проверяй состояние Git.** Не приписывай репозиторию изменения,
   которые ещё не смержены.
3. **Не дублируй источники истины.** У проекта должны быть понятные
   места хранения правил и технической информации (например, Git
   Workflow — в `dev-docs/git-workflow.md`, а не в копиях).
4. **Не раздувай документацию.** Предпочитай конкретные инструкции и
   факты длинным общим описаниям.
5. **Не удаляй полезную информацию без причины.** При реорганизации
   сохраняй актуальное содержание.
6. **Не придумывай факты.** При недостатке информации отмечай
   неопределённость и сообщай, что нужно проверить.
7. **Учитывай уровень команды.** Инструкции должны быть понятны
   начинающим разработчикам, участвующим в SENIO.
8. **Соблюдай существующий стиль и структуру проекта**, если нет веских
   оснований их менять.

## Разделение ответственности

Этот Skill отвечает только за **процесс** работы с документацией.
Проектные сведения, архитектурные решения, правила разработки и
ограничения хранятся в документах проекта, прежде всего в `AGENTS.md`.
Не помещай весь контекст SENIO внутрь этого Skill.

Перед выполнением работы обязательно изучай актуальные `AGENTS.md` и
следуй им. Правила Git, коммитов, PR и ревью не дублируй здесь:
источник истины — `AGENTS.md` и `dev-docs/git-workflow.md`.

## Ограничения

- Не изменяй исходный код приложения.
- Не меняй Docker, CI/CD и конфигурацию инфраструктуры ради
  документации.
- Не изменяй Issues, Pull Requests, GitHub Rulesets и другие внешние
  ресурсы.
- Не создавай коммиты и не отправляй изменения в удалённый репозиторий
  без явного разрешения пользователя.
- Не удаляй документы без обоснованной необходимости.

Остальные правила работы с Git и внешними сервисами — в `AGENTS.md`.

## Результат

В итоговом ответе перечисли:

- какие документы изменены и что именно в них исправлено;
- какие проверки выполнены (ссылки, команды, сверка с кодом и Git);
- какие сведения проверить не удалось и почему.
