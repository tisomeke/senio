# AGENTS.md --- SENIO

Инструкции для ИИ-агентов, работающих с репозиторием SENIO. Этот файл
описывает подтверждённое состояние репозитория на момент проверки;
обновляй его, если структура или процессы проекта изменятся.

## 1. Контекст проекта

SENIO --- студенческий проект для организации, поиска и обмена учебными
материалами.

**Текущее состояние:** проект вышел из стадии пустого репозитория.
Инициализировано Django-приложение (`config/`, `manage.py`,
`requirements.txt`), настроен запуск через Docker (`Dockerfile`,
`compose.yaml`, `.env.example`, `.dockerignore`) и CI через GitHub
Actions (`.github/workflows/ci.yml`). В `README.md` есть описание
проекта и инструкция запуска для разработчиков.

Прикладная функциональность пока не реализована: нет каталога
материалов, авторизации, загрузки файлов, поиска, модерации и
AI-функций.

Не представляй планы как реализованные возможности. Не утверждай, что
существуют функции, которых нет в коде, и не приписывай репозиторию
изменения, которые ещё не смержены в `main`.

## 5. Правила написания кода

Поскольку прикладной код и соглашения по стилю пока не обнаружены:

-   ориентируйся на существующий код и конфигурацию инструментов, если
    они появятся;
-   выбирай понятные имена, небольшие функции и модули с ясной
    ответственностью;
-   не добавляй типизацию, форматтеры, линтеры или дополнительные
    библиотеки только ради формального стандарта;
-   избегай дублирования, но не создавай абстракцию для единственного
    простого случая без обоснованной пользы;
-   обрабатывай ошибки там, где их можно корректно обработать; не
    скрывай ошибки пустыми `except` и не используй `print` вместо
    принятого в проекте логирования;
-   храните конфигурацию отдельно от кода, а секреты --- только в
    локальном окружении или предназначенном для них хранилище.

Когда появятся реальные соглашения в коде или настройках инструментов,
они имеют приоритет над этими общими рекомендациями.

(`ruff check .` для Python и actionlint для workflow-файлов, оба

`.github/workflows/ci.yml`.

При изменении кода:

-   добавляй или обновляй тесты, если в проекте появится подходящая
    тестовая инфраструктура;
-   проверяй изменённое поведение и связанные сценарии;
-   запускай только существующие и настроенные проверки;
-   в итоговом сообщении явно указывай, что запускалось и с каким
    результатом.

Не заявляй, что тесты, линтер или сборка прошли, если они не
запускались. Если автоматических проверок нет, честно укажи это и опиши
выполненную ручную проверку.

## 7. Безопасность

-   Не добавляй в репозиторий пароли, токены, ключи, реальные
    пользовательские данные или содержимое локальных `.env`-файлов.
-   Перед добавлением файлов проверяй `git diff` и статус репозитория,
    чтобы случайно не включить локальные настройки и секреты.
-   Не ослабляй проверки безопасности и не добавляй обходные решения
    только ради прохождения проверки.
-   Если в будущем появятся загрузки материалов, проверяй тип, размер и
    допустимость файлов на серверной стороне; не считай клиентскую
    проверку достаточной.
-   Не придумывай требования к хранению файлов или внешним сервисам до
    появления соответствующей архитектуры.

## 8. Git Workflow

Обязательные правила описаны в
[`dev-docs/git-workflow.md`](dev-docs/git-workflow.md). Ключевые
положения:

-   не работай непосредственно в `main`;
-   используй отдельную ветку на задачу и Pull Request для изменений;
-   именуй ветки и коммиты по соглашениям из Git Workflow;
-   связывай каждый PR с соответствующей Issue;
-   перед завершением проверяй `git status` и `git diff`;
-   дождись ревью и согласования перед слиянием; не сливай собственный
    PR без согласования команды;
-   не используй `git push --force` и не переписывай историю общей ветки
    без согласования.

Не выполняй `commit`, `push`, создание PR, слияние или другие действия
во внешних сервисах, если пользователь явно не разрешил именно это
действие. Просьба подготовить или проверить изменения не является
разрешением применить их.

## 9. Принципы работы ИИ-агента

1.  Перед изменениями изучи связанный код, документацию и состояние Git.
2.  Уточни цель задачи и её границы. Если неоднозначность влияет на
    продуктовое поведение, безопасность или архитектуру, сообщи о ней до
    реализации.
3.  Выбирай простейшее решение, достаточное для задачи. Не усложняй MVP
    преждевременными абстракциями, библиотеками, сервисами или
    архитектурными слоями.
4.  Меняй только относящиеся к задаче файлы. Не выполняй несвязанный
    рефакторинг и не переписывай большие участки кода, если достаточно
    локального изменения.
5.  Не выдавай предположения за факты. Проверяй наличие файлов,
    настроек, команд и возможностей перед тем, как на них ссылаться.
6.  Не перезаписывай пользовательские изменения. Если в рабочем дереве
    есть незнакомые или несвязанные изменения, сохрани их и сообщи о
    возможном конфликте.
7.  Не выполняй разрушительные команды, не удаляй данные и не меняй
    настройки окружения без явной необходимости и разрешения.
8.  Не выполняй действия во внешних сервисах без явного разрешения
    пользователя на конкретное действие. Подготовка текста, плана или
    патча не означает разрешения отправить его, применить к репозиторию,
    создать PR или изменить настройки.
9.  После изменений запускай доступные релевантные проверки. Если
    проверить что-либо невозможно, прямо укажи причину.
10. В итоговом ответе кратко перечисли изменения, фактически выполненные
    проверки и оставшиеся ограничения. Не утверждай, что работа
    выполнена или проверена, если это не так.
